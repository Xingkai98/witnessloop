# Proposal: adopter-test-gate（接入方的测试要进 CI，并且**是机械的**）

> 状态：草稿（**v2 · 方向反转**——见「为什么反转」）。
> 关联 issue：witnessloop **#4**。

## 背景

`init` 写的 caller workflow **只跑 `witnessloop check`**（`initcmd.caller_workflow`，`initcmd.py:24-40`）——
接入方自己的测试**没有任何自动执行点**：

- 实证（issue #4 来源）：M3 acid test 的 `add-greeting` change 引入了 `tests/test_greeting.py`（13 个用例），
  真实 PR 运行 `38040394810` 的 job 列表**只有 `gate / check` 一项**，**pytest 一次都没跑**。
- 与流程要求冲突：流程规定「实现阶段 TDD、审阅者核实测试通过」（出处 `templates/review-loop.md:33,69,77`）
  ——**审阅者只能靠人工记忆跑一次**，没有 CI 兜底。
- 对照：asterwynd 自己的 `ci.yml` 跑全量 pytest；本仓也有 `ci.yml` 的 `test` job——**但那是自测，不是给接入方的**。
- ⇒ 接入方拿到的是**只看流程证据、不看代码好坏**的门禁。

## 为什么反转（v1 → v2）

v1 稿（以及它的 grill + 两轮对抗验证）收敛成「**只交付模板 + 文档**」，理由是两条**假想约束**：
「已接入的仓拿不到新东西」（`_already_initialized` 早返回）与「换 ref 会让存量接入方撞死锁」。

**用户指出这两条前提不成立**（2026-10-13），已核实：

- **没有任何外部接入方**：`gh search code --owner Xingkai98 witnessloop` 空；`gh repo list` 里唯一的候选是
  **`wl-test`**（用户自己的一次性 acid test 仓、私有、可删）——它确实是「已接入」且钉 `@v1`。
- 本仓自己（dogfood）是另一个「接入方」——而它的 caller 同样钉 `@v1`。

⇒ **「存量」这条约束消失**，于是「只能给文档」这个结论也随之消失：
`init` 可以**一次性把测试执行点写进去**（接入方永远不必手改生成物 ⇒ 死锁路自然不走），
`check` 可以**机械地要求**它存在，测试可以**跑在门禁里**。

**用户的要求（2026-10-13 原话概括）**：「有 CI 测试强制得有。如果没有 CI 测试的话，这个就会有问题」
⇒ 本 change 交付**机械**版本，issue #4 届时可名正言顺关闭。

## 目标

1. **`init` 就把测试执行点写进去**（命令在接入时给：`init --test-command "<cmd>"`），接入方**无需手改任何生成物**。
2. **测试跑在门禁里** ⇒ 测试失败 = required check 失败 = **合不了**。
3. **`check` 机械地要求「测试执行点存在且已接线」**：策略声明了执行点而它缺失/仍是未替换的哨兵 ⇒ **红**
   （「没有 CI 测试」这件事本身要被拦住，而不是给一行礼貌提醒）。
4. 命令**以后能自由改**（不撞台账死锁）：命令住**接入方自己的、非台账**的文件里。
5. **顺带修掉一个正在漏的事**：`init` 写 `@v1`，而主干领先 6 个提交（含 #13/#16 的新门禁）
   ⇒ **任何新功能都到不了接入方**，且**本仓自己的 PR 检查跑的是 6 个提交前的 CLI**（对抗轮 B1 实测：
   同一个 diff，v1 报 1 条、main 报 4 条）⇒ 本 change 必须把「发版/ref」这一步定下来。

## 非目标

- **不让 `check` 去执行测试**（跑测试是 CI 侧 job 的职责；`check` 只做「执行点在不在、接线没接线」的存在性判定）。
- **不做测试命令探测**（显式优于魔法）。
- **不用「手改 `init` 产物」当配置通道**（实测死锁：`init`/`uninit` 同时 exit 1，无 flag 可确认）。
- 不引入运行时依赖（`dependencies = []` 保持；判定只做**文件存在 + 字符串**检查，不解析 YAML）。
- 不替接入方勾 required（平台侧仍是一次人工操作）——但选「测试与 `check` 同 job」时**不需要新增**勾选。

## 验收

- 单测：`init` 写出的执行点文件 / caller / policy 的形态（pyyaml + 既有 `tests/test_init*.py` 手法）；
  `check` 在「执行点缺失 / 未替换哨兵 / 已接线」三态下的判定；
  既有幂等 / 冲突 / `uninit` 回滚用例全绿。
- 端到端：真实仓 `init --test-command "…"` ⇒ 门禁能跑该命令；命令失败 ⇒ check 红。
- 本 change 自己走完整流程（契约 + 证据 + `check` + PR）。
