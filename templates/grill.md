# 模板：grill（设计对抗式追问）

> **host 中立模板。** 这里只有算法与 prompt 文本，不含任何 host 专有语法。
> 各 host 的适配器负责把它接到自己的命令入口（去哪找适配器由该 host 的发行方式决定，
> 本文件不指向任何具体目录）。
> **适配器不得复制本正文**——只引用本文件路径，物理分离是为了日后能换 host。

## 目的

在写代码**之前**，用一个**独立零记忆**的审阅者把 design 追问到完备，再让**另一个**
独立审阅者**证伪**这些结论，收敛之后**才**把真正需要人拍板的问题交给用户，
最后把结果整合回 `design.md`。

要防的不是「写不出来」，而是「跳过设计直接写」「自己拍板自己实现」。

## 时序（**先收敛，后停轮**——别做反）

```
grilling pass（审阅者独立求完备，用户不参与）
      ↓
设计阶段对抗验证 loop（另起审阅者，证伪 → 修 → 再审，直到 PASS 或封顶）
      ↓
停轮：把收敛后的 Open Questions 一次性交用户确认
      ↓
把对抗验证的必须修改整合回 design.md
```

**用户只被停一次，且在对抗收敛之后。** 反过来（每轮都停下来问用户、对抗验证排最后）
是错的：那会把未经证伪的结论先塞给用户拍板，也把用户的注意力浪费在审阅者自己
查得到的问题上。

## 参与者

- **作者**：写 design 的那个 run。
- **审阅者**：**必须另起一个 run**，零记忆、不共享上下文、不读作者的会话历史。
  同一 run 既写又审等于没审。（对抗验证阶段**再另起一个**。）

## 输入

- `<changes_root>/<change-id>/design.md`（以及 `proposal.md`）
- 目标仓的 policy（受保护路径、必需 artifact、`require_change_for`）
- 相关的既有代码/spec（只读）

## Grill 维度（逐项追问）

1. **需求对齐**：design 是否覆盖 proposal 的目标、边界、验收标准。
2. **实现细节**：每个 Decision 是否有具体方案、备选、理由；还有哪些细节没定。
3. **依赖**：是否依赖尚未就绪的模块 / 规格 / 外部系统。
4. **风险**：边界条件、失败模式、性能。
5. **测试策略**：关键路径有没有测试计划，怎么证明它对。
6. **文档影响**：是否需同步 spec / 其他文档 / 使用说明。
7. **触发与门禁**：若本 change 改的是门禁或检查器本身，**它自己会不会死锁或误伤**
   （例如本 change 的写操作是否恰好命中自己要新增的规则）。

## 执行步骤

### 1. 定位 change

确定 `change-id` 与 change 目录。参数缺省时从上下文或当前分支推断，别猜。

### 2. 起零记忆审阅者

**另起一个 run** 当审阅者，零记忆：不读作者的会话历史、不共享上下文，
只读 change 目录里的文本与只读的仓库内容。把上面 7 个维度、以及「**挑战而非确认**」
的要求交给它：触发条件够准吗？会不会误伤或死锁？证据格式可机械解析吗？
与既有机制冲突吗？逐项追问，不要放过。

### 3. 按设计树求完备（审阅者独立完成，**此阶段不停轮给用户**）

把设计想成一棵**设计树**：每个决策分出依赖它的下游决策。
**frontier 的定义**：所有「前置已定」的决策点——现在就能处理、不必猜未答答案的那些。

审阅者**在内部**按轮推进 frontier（这轮问不完就重算 frontier 走下一轮），
每一轮把当前 frontier **逐条分流**：

- **需要环境事实**的（文件、工具输出、既有实现）→ **另起一个 run 去查**，
  不要问用户任何你自己查得到的东西。**但不要阻塞**：正在探查、尚未回来的事实
  本身就是一个**未决前置**——**只有它下游的问题**该等它，**其余 frontier 现在就照处理**，
  别因为一个事实没查到就把整条 frontier 扣下。
- **能由代码或规格直接判定**的 → **Code-Resolved Questions**：带 `文件:行号` 证据
  **自行定案**，记进决策记录，**不进 `## Open Questions`、不停轮**。
- **只有真正需要人取舍的** → 留下来，成为 `## Open Questions`。

依赖本轮仍未决问题的问，**归下一轮**——不要在同一轮里猜那些答案。

**完成条件 = frontier 为空**：设计树的每个分支都走到过，没有什么是被默默假设的。
走到这里，`## Open Questions` 里剩下的应当**只有**用户取舍。

### 4. 产出决策记录

写 `<change-dir>/reviews/grill-review.md`（即 `grill-design.md`），结构：

```markdown
# Grill: <change-id> 设计追问

## Reviewer
- run id: <审阅者 run id>
- 时间: <UTC 时间>

## Confirmed Decisions
- **决策**：<内容>；理由：<理由>；来源: <run id>
- ……（**至少 3 条**，每条都要有 `来源:`）

## Code-Resolved Questions
- <问题> → <结论>（证据：<文件:行号>）

## Open Questions
- **Q1** <问题标题>：<问题正文，落到具体例子或场景>
  - ➡️ **推荐答案**：<你的推荐>
- ……（可为空）

## 风险
- <新发现的风险>
```

`## Confirmed Decisions` **至少 3 条**、每条附 `来源: <run id>` 是**硬门槛**：
下游的检查器按这个格式解析，少一条或少了来源就当作证据不合格。

`## Open Questions` 每条都要给**推荐答案**与**具体例子或场景**——「一般来说没问题」
不算，用户在停轮时要能快速判断。

### 5. 设计阶段对抗验证 loop（**在停轮之前**跑完）

这个 loop 与实现后的审阅闭环**同构**：另起独立零记忆审阅者 → 对抗 → verdict →
修 → 再审。

- **另起一个独立零记忆的审阅者**，**默认上面的结论有错**，逐条去**证伪**
  Confirmed Decisions 与 Open Questions——不是复述，是尝试推翻。能实测/复现的就去实测。
- 出 **verdict**：`PASS` / `CHANGES_REQUESTED`。
- `CHANGES_REQUESTED` 则**修 `grill-review.md`（grill-design.md）** 并**再审**，
  直到 `PASS` 或**轮数封顶**（默认 3 轮，到顶交人判断）。
- 产物 `<change-dir>/reviews/grill-adversarial.md`（verdict + 逐条 issue `文件:行号`
  + 对抗结论 + Code-Resolved 答案）。
- **被证伪的决策要回写 `grill-review.md`**——这一步必须在**停轮之前**做完，
  别把没经证伪的结论拿去让用户拍板。

### 6. 才停轮：把收敛后的 Open Questions 一次性交给用户

走到这里才停。把 `## Open Questions`（**收敛后的版本**）**一次性**逐条抛给用户，
每条附推荐答案与具体例子。**审阅者不得替用户拍板**，也不得把自己写的文本
当成用户的确认。

用户答复后，逐条写进决策记录的 `## User Confirmation` 段：
确认了什么 + 依据 + 时间。

### 7. 整合回 design.md

- 把对抗验证的**必须修改**项整合进 `design.md` 的 Decision（新增或修正原文）。
- 更新 `design.md` 的 `## Pre-Implementation Review` 节：记下已确认决策、
  **必须修改（已整合）**、以及 Code-Resolved 结论。
- 若发现**阻塞性设计缺陷** → 停，向用户报告，等指示。

## 怎么取 run id

`reviewer_run_id` 与 `author_run_id` 是身份字段（自由文本，**防漂移不防伪造**）。
各 host 的适配器按**同一套**规则取值，别各自发明：

1. **环境优先**：读 `WITNESSLOOP_RUN_ID`（当前 run 的 id）。审阅者与作者是**不同的
   run**，各自的环境里这个值本就应当不同。同一进程里要同时给两个角色时，用角色
   专用变量（优先级更高）：`WITNESSLOOP_REVIEWER_RUN_ID` / `WITNESSLOOP_AUTHOR_RUN_ID`。
2. **取不到就生成**一个唯一 id，形态 `<stage>-<role>-<UTC 时间戳>-<短随机>`。
   把 `role` 编进 id，是为了让生成路径下两个角色**必然不同**。
3. **两者必须不同**：`manifest build` 对相等直接拒——那正是「忘了另开 run」的症状。
   只设共享的 `WITNESSLOOP_RUN_ID` 会让两个角色拿到同一个值、被门禁拦下，这不是 bug。

## 产物

- `<change-dir>/reviews/grill-review.md`（`grill-design.md`）：决策记录
  （Confirmed Decisions / Code-Resolved Questions / Open Questions / 风险 /
  User Confirmation）。
- `<change-dir>/reviews/grill-adversarial.md`：对抗验证报告。
- `design.md` 的 `## Pre-Implementation Review` 节：必须修改已整合。
- 随后用 `witnessloop manifest build` 把它们落成 manifest（报告 + manifest 成对）。

## 硬约束

- **缺证据不得进入实现**。四件事**全部**满足之前，**不得**开始写代码：
  1. `frontier` 为空（设计树求完备）；
  2. 对抗验证已到 `PASS`（或轮数封顶并交人）；
  3. `## Open Questions` 已由用户逐条确认、记入 `## User Confirmation`；
  4. `## Confirmed Decisions` ≥3 条且每条带 `来源:`。
  这是门禁的前置条件，不是建议。
- **时序**：先收敛（第 3、5 步），**再**停轮（第 6 步）——别做反。
- 审阅者 ≠ 作者；审阅者对 change 状态**只读**，**不得持有自己的状态文件**——
  一切以 manifest 为准。
- 报告里的身份字段（审阅者 run id / 作者 run id）是自由文本：本工具**防漂移、
  不防蓄意伪造**，别把它当成签名。
