# 模板：grill（设计对抗式追问）

> **host 中立模板。** 这里只有算法与 prompt 文本，不含任何 host 专有语法。
> 各 host 的适配器负责把它接到自己的命令入口（去哪找适配器由该 host 的发行方式决定，
> 本文件不指向任何具体目录）。
> **适配器不得复制本正文**——只引用本文件路径，物理分离是为了日后能换 host。

## 目的

在写代码**之前**，用一个**独立零记忆**的审阅者对 design 逐轮追问，把「没人验证过的
假设」逼成「有依据、有人拍板的决策」，并留下可提交、可审计的决策记录。

要防的不是「写不出来」，而是「跳过设计直接写」「自己拍板自己实现」。

## 参与者

- **作者**：写 design 的那个 run。
- **审阅者**：**必须另起一个 run**，零记忆、不共享上下文、不读作者的会话历史。
  同一 run 既写又审等于没审。

## 输入

- `<changes_root>/<change-id>/design.md`（以及 `proposal.md`）
- 目标仓的 policy（受保护路径、必需 artifact、`require_change_for`）
- 相关的既有代码/spec（只读）

## 步骤

1. **列决策点**：审阅者只读 design，把其中的技术选择、边界假设、隐含前提逐条列出来。
2. **逐条追问**：对每个决策点问反例、问边界、问与既有约束的冲突、问失败模式、
   问「换一个实现会怎样」。每条追问都要落到一个**具体例子**或场景上，
   不接受「一般来说没问题」这种回答。
3. **产出两部分**：
   - `## Confirmed Decisions`：已有依据钉死的决策，逐条附依据（谁/什么证据）。
   - `## Open Questions`：仍需人拍板的问题。**每条必须配一个具体例子 + 一个推荐答案**
     （推荐可以不采纳，但必须给，否则是把判断成本原样丢回给人）。
4. **停轮**：把 `Open Questions` 交给用户逐条确认。**审阅者不得替用户拍板**，
   也不得把自己写的文本当成用户的确认。
5. **记录确认**：用户答复后，把结论写进决策记录的 `## User Confirmation` 段，
   逐条写明「确认了什么 + 依据 + 时间」。

## 怎么取 run id

`reviewer_run_id` 与 `author_run_id` 是身份字段（自由文本，**防漂移不防伪造**）。
各 host 的适配器按**同一套**规则取值，别各自发明：

1. **环境优先**：读 `WITNESSLOOP_RUN_ID`（当前 run 的 id）。审阅者与作者是**不同的
   run**，各自的环境里这个值本就应当不同。同一进程里要同时给两个角色时，用角色
   专用变量（优先级更高）：`WITNESSLOOP_REVIEWER_RUN_ID` / `WITNESSLOOP_AUTHOR_RUN_ID`。
2. **取不到就生成**一个唯一 id，形态 `<stage>-<role>-<UTC 时间戳>-<短随机>`。
   把 `role` 编进 id，是为了让生成路径下两个角色**必然不同**。
3. **两者必须不同**：`manifest build` 对相等直接拒——那正是「忘了另开 run」的症状。
   只设共享的 `WITNESSLOOP_RUN_ID` 会让两个角色拿到同一个值、被门禁拦下，这不是 bug。

## 产物

- `<change-dir>/reviews/grill-review.md`：决策记录（Confirmed Decisions /
  Open Questions / User Confirmation）。
- 随后用 `witnessloop manifest build` 把它落成 manifest（报告 + manifest 成对）。

## 硬约束

- **缺证据不得进入实现**：`## User Confirmation` 为空、或缺了任何一条 Open Question
  的答复时，**不得**开始写代码。这一步是门禁的前置条件，不是建议。
- 审阅者 ≠ 作者；审阅者对 change 状态**只读**，**不得持有自己的状态文件**——
  一切以 manifest 为准。
- 报告里的身份字段（审阅者 run id / 作者 run id）是自由文本：本工具**防漂移、
  不防蓄意伪造**，别把它当成签名。
