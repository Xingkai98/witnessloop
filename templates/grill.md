# 模板：grill（设计对抗式追问）

> **host 中立模板。** 这里只有算法与 prompt 文本，不含任何 host 专有语法。
> 各 host 的适配器负责把它接到自己的命令入口（去哪找适配器由该 host 的发行方式决定，
> 本文件不指向任何具体目录）。
> **适配器不得复制本正文**——只引用本文件路径，物理分离是为了日后能换 host。

## 目的

在写代码**之前**，用一个**独立零记忆**的审阅者对 design 逐轮追问，把「没人验证过的
假设」逼成「有依据、有人拍板的决策」，再让另一个独立审阅者**证伪**这些结论，
最后把结果落成可提交、可审计的决策记录。

要防的不是「写不出来」，而是「跳过设计直接写」「自己拍板自己实现」。

## 参与者

- **作者**：写 design 的那个 run。
- **审阅者**：**必须另起一个 run**，零记忆、不共享上下文、不读作者的会话历史。
  同一 run 既写又审等于没审。（对抗验证阶段再另起一个。）

## 输入

- `<changes_root>/<change-id>/design.md`（以及 `proposal.md`）
- 目标仓的 policy（受保护路径、必需 artifact、`require_change_for`）
- 相关的既有代码/spec（只读）

## Grill 维度（逐项追问）

1. **需求对齐**：design 是否覆盖 proposal 的目标、边界、验收标准。
2. **实现细节**：每个 Decision 是否有具体方案、备选、理由；还有哪些细节没定。
3. **依赖**：是否依赖尚未就绪的模块 / 规格 / 外部系统。
4. **风险**：边界条件、失败模式、性能。
5. **测试策略**：关键路径有没有测试计划，怎么证明它对。
6. **文档影响**：是否需同步 spec / 其他文档 / 使用说明。
7. **触发与门禁**：若本 change 改的是门禁或检查器本身，**它自己会不会死锁或误伤**
   （例如本 change 的写操作是否恰好命中自己要新增的规则）。

## 执行步骤

### 1. 定位 change

确定 `change-id` 与 change 目录。参数缺省时从上下文或当前分支推断，别猜。

### 2. 起零记忆审阅者

**另起一个 run** 当审阅者，零记忆：不读作者的会话历史、不共享上下文，
只读 change 目录里的文本与只读的仓库内容。把上面 7 个维度、以及「**挑战而非确认**」
的要求交给它：触发条件够准吗？会不会误伤或死锁？证据格式可机械解析吗？
与既有机制冲突吗？逐项追问，不要放过。

### 3. 多轮 frontier 循环（**这是本流程的主体，不是一趟**）

把设计想成一棵**决策树**：每个决策分出依赖它的下游决策。**按轮走**。

**frontier 的定义**：所有「前置已定」的决策点——也就是**现在就能问、不必猜未答答案**
的那些。每轮只问 frontier。

每一轮：

1. **一次性抛出整条 frontier**，按下面格式给**编号**，**每条附推荐答案**。
   问题要落到**具体例子或场景**上——「一般来说没问题」不算答复，
   「在 X 场景下会怎样」才是：

   ```
   ❓ **Q1** — **<问题标题>**：<问题正文，可以多段、可以给多选>

   ➡️ <你的推荐答案>

   ---

   ❓ **Q2** — **<问题标题>**：<问题正文>

   ➡️ <你的推荐答案>
   ```

2. **抛完就停下**，等用户逐条答复，**不得**在没听到答复前自问自答往下走。
3. 用户答复**重塑这棵树**：已定的决策把 frontier 往外推，解锁依赖它们的问题。
   **重算 frontier**，再问下一轮。
4. **依赖本轮仍未决问题的问，属于下一轮**，不属于本轮——不要在同一轮里猜那些答案。
5. **完成条件 = frontier 为空**：设计树的每个分支都走到过，没有什么是被默默假设的。
   在用户确认已达成共识之前，**不要**按这棵树行动。

**事实是你的活，不是用户的**：frontier 里某个问题需要环境事实（文件、工具输出、
既有实现）时，**另起一个 run 去查**，不要问用户任何你自己查得到的东西。
同理，能由代码或规格直接判定的 **Code-Resolved Questions**：带 `文件:行号` 证据
**自行定案**并记进决策记录，**不进 frontier、不停轮**；只把真正需要人取舍的问题
留给用户。

### 4. 产出决策记录

写 `<change-dir>/reviews/grill-review.md`，结构：

```markdown
# Grill: <change-id> 设计追问

## Reviewer
- run id: <审阅者 run id>
- 时间: <UTC 时间>

## Confirmed Decisions
- **决策**：<内容>；理由：<理由>；来源: <run id>
- ……（**至少 3 条**，每条都要有 `来源:`）

## Code-Resolved Questions
- <问题> → <结论>（证据：<文件:行号>）

## Open Questions
- <未决项>（可为空）

## 风险
- <新发现的风险>
```

`## Confirmed Decisions` **至少 3 条**、每条附 `来源: <run id>` 是**硬门槛**：
下游的检查器按这个格式解析，少一条或少了来源就当作证据不合格。

### 5. 对抗验证（`grill-adversarial`）

grill 结论产出后、**停轮之前**，再**另起一个独立零记忆的审阅者**做对抗验证：
**默认上面的设计结论有错**，逐条去**证伪**——不是复述，是尝试推翻。
能实测/复现的就去实测。给出 verdict（`PASS` / `CHANGES_REQUESTED`），
`CHANGES_REQUESTED` 则修完再审，直到 `PASS` 或轮数封顶（默认 3 轮，到顶交人判断）。
产物 `<change-dir>/reviews/grill-adversarial.md`。

### 6. 整合回 design.md

- 把验收出的**必须修改**项整合进 `design.md` 的 Decision（新增或修正原文）。
- 更新 `design.md` 的 `## Pre-Implementation Review` 节：记下已确认决策、
  **必须修改（已整合）**、以及 Code-Resolved 结论。
- 若发现**阻塞性设计缺陷** → 停，向用户报告，等指示。

### 7. 记录用户确认

用户对 frontier 的答复逐条写进决策记录的 `## User Confirmation` 段：
确认了什么 + 依据 + 时间。**审阅者不得替用户拍板**，也不得把自己写的文本
当成用户的确认。

## 怎么取 run id

`reviewer_run_id` 与 `author_run_id` 是身份字段（自由文本，**防漂移不防伪造**）。
各 host 的适配器按**同一套**规则取值，别各自发明：

1. **环境优先**：读 `WITNESSLOOP_RUN_ID`（当前 run 的 id）。审阅者与作者是**不同的
   run**，各自的环境里这个值本就应当不同。同一进程里要同时给两个角色时，用角色
   专用变量（优先级更高）：`WITNESSLOOP_REVIEWER_RUN_ID` / `WITNESSLOOP_AUTHOR_RUN_ID`。
2. **取不到就生成**一个唯一 id，形态 `<stage>-<role>-<UTC 时间戳>-<短随机>`。
   把 `role` 编进 id，是为了让生成路径下两个角色**必然不同**。
3. **两者必须不同**：`manifest build` 对相等直接拒——那正是「忘了另开 run」的症状。
   只设共享的 `WITNESSLOOP_RUN_ID` 会让两个角色拿到同一个值、被门禁拦下，这不是 bug。

## 产物

- `<change-dir>/reviews/grill-review.md`：决策记录（Confirmed Decisions /
  Code-Resolved Questions / Open Questions / 风险 / User Confirmation）。
- `<change-dir>/reviews/grill-adversarial.md`：对抗验证报告。
- `design.md` 的 `## Pre-Implementation Review` 节：必须修改已整合。
- 随后用 `witnessloop manifest build` 把它们落成 manifest（报告 + manifest 成对）。

## 硬约束

- **缺证据不得进入实现**：`frontier` 不为空、`## Confirmed Decisions` 少于 3 条、
  `## User Confirmation` 未记录、或对抗验证未到 `PASS` 时，**不得**开始写代码。
  这是门禁的前置条件，不是建议。
- 审阅者 ≠ 作者；审阅者对 change 状态**只读**，**不得持有自己的状态文件**——
  一切以 manifest 为准。
- 报告里的身份字段（审阅者 run id / 作者 run id）是自由文本：本工具**防漂移、
  不防蓄意伪造**，别把它当成签名。
